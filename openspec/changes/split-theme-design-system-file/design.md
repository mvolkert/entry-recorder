# Design

## Context

See proposal.md — Why. `Theme.kt` mixes declarative data (the eight curated `accentPresets`, whose literals are
generated by `tools/derive_accents.py` and re-checked every run by `AccentPaletteContrastTest`), pure mappings
(`statusColorFor`, `eventTypeIcon`, `monitorStatusColor`), `@Composable` readers (`disabledContentColor`,
`recordingGlyphColor`, the three label composables), a non-composable token object (`Spacing`), and the `AppTheme`
root that resolves dark/light, applies dynamic colour, and drives the edge-to-edge bar icon contrast. The presets
carry a load-bearing comment ("do not hand-edit a single role, re-run the script") that a reader currently has to
scroll past to reach `AppTheme`.

## Goals / Non-Goals

**Goals:**
- One concern per file, with the generated-value files (`Accents.kt`, `StatusColors.kt`) separated from the
  entry point so a colour edit does not touch `AppTheme`.
- The derive-script warning travels with the presets it describes.
- Zero visual delta: same colours, same `when` arms, same composition locals.

**Non-Goals:**
- No re-layering of the theme (no `designsystem` module, no moving `Spacing` into `domain`), no renaming toward
  Material 3 token names, and no change to the Material3 motion-scheme workaround.
- No new public API surface: every symbol already public stays public with the same signature.

## Decisions

- **Split by kind, not by feature.** Colour data (`Accents.kt`, `StatusColors.kt`), scalar/composable tokens
  (`Tokens.kt`), string labels (`Labels.kt`), preference enum (`ThemeMode.kt`), entry point (`Theme.kt`).
  Alternative — one file per Material theme facet (`Color.kt` / `Typography.kt` / `Shape.kt`) — rejected: this
  project has no typography or shape layer in `Theme.kt`, so the canonical triad would be empty files.
- **`buildColorScheme` moves with the presets to `Accents.kt`.** It exists only to assemble `AccentRoles` triples
  into a `ColorScheme`; keeping it in `Theme.kt` would split one mechanism across two files. `AppTheme` then reads
  as resolution → dynamic-or-curated → insets → `MaterialExpressiveTheme` only.
- **`LocalDarkTheme` stays in `Theme.kt`** with the code that provides it, so the composition-local owner and its
  producer are adjacent; `recordingGlyphColor()` (a consumer via `LocalDarkTheme`) moves to `Tokens.kt` and
  imports it — an intra-package import, no cycle because neither file depends on the other's *initialisers* at
  class-load time.
- **`monitorStatusColor` belongs with the status palette**, not with neutral tokens, because both map a
  connectivity concept to a colour and the contrast test already groups them.
- **File moves only, one commit per new file**, so a reviewer can diff each move against the original block and
  confirm no literal changed.

## Risks / Trade-offs

- [A pasted accent literal silently differs after the move] → `AccentPaletteContrastTest` and
  `StatusPaletteContrastTest` run unmodified; additionally the move commits must show deletions and additions of
  identical literal text (`git diff --color-moved` check noted in tasks).
- [Compose compiler sees more files → recomposition behaviour changes] → no: skippability depends on parameters
  and stability, not file layout; `lintDebug` + a UI smoke pass confirm.
- [`derive_accents.py` docstring points at a now-nonexistent home] → task 6 updates its two references; the
  script does not parse Kotlin, so there is no functional coupling to break.

## Migration Plan

Six mechanical moves, starting with the symbols nothing else in the file defines (`ThemeMode.kt` → `Accents.kt`
→ `StatusColors.kt` → `Tokens.kt` → `Labels.kt`), finishing by slimming `Theme.kt` down to `AppTheme` and
`LocalDarkTheme`. Each commit is independent, so rollback is reverting the one that misbehaved.
